# Installer Staged Database Import Design

## Goal

Add the first database import execution path inside the standalone installer by importing backup SQL chunks into isolated staging tables, without replacing destination tables.

## Context

The installer can now:

- validate the staged archive
- require token access and explicit restore confirmation
- prepare a rollback artifact
- copy destination `wp-config.php`
- dump destination database rollback SQL when possible
- show database connection and rollback dump status

The next risky step is importing backup database content. This slice deliberately stops before table replacement. It proves that backup SQL chunks can be read, validated, rewritten to staging table names, and executed into the destination database using installer credentials.

## Recommended Approach

Use a staged import MVP:

1. Read `database/tables.json` from the staged backup ZIP.
2. Validate table records and chunk file names.
3. For each source table, create a deterministic staging table name.
4. Read chunk SQL from `database/chunks/<chunk>`.
5. Rewrite SQL identifiers from source table names to staging table names.
6. Execute rewritten SQL against the destination database.
7. Record import metadata in `config.php`.
8. Render a Bootstrap UI action and status.

No destination table is dropped, renamed, truncated, or replaced in this slice.

## Scope

Included:

- Parse and validate backup database manifest from the staged archive.
- Validate chunk file names are safe basenames ending in `.sql`.
- Read SQL chunk contents from the staged archive.
- Rewrite only table identifiers that match exported table names.
- Execute SQL chunks into staging tables.
- Track imported table count, chunk count, staging table map, and timestamp in installer config.
- Bootstrap action gated by token, confirmation, rollback preparation, and database rollback dump.

Excluded:

- Destination table replacement/swap.
- Dropping destination tables.
- URL replacement during import.
- File extraction/restore.
- Rollback execution.
- Long-running progress polling.
- Manual DB credential entry.
- SQL parsing beyond the constrained dump format generated by this plugin.

## Components

### `DatabaseImportManifestReader`

New installer class:

`super-sheep-copy/installer/restore-engine/DatabaseImportManifestReader.php`

Responsibilities:

- Open staged archive with `ZipArchive`.
- Read `database/tables.json`.
- Decode JSON as array.
- Validate `format_version`, `table_count`, and `tables`.
- For each table, validate:
  - non-empty string `name`
  - `chunks` is a list
  - each chunk name is a safe basename ending in `.sql`
  - chunk entry exists under `database/chunks/`
- Return a normalized manifest array with table records.

It must not extract archive entries to disk.

### `SqlTableNameRewriter`

New installer class:

`super-sheep-copy/installer/restore-engine/SqlTableNameRewriter.php`

Responsibilities:

- Accept SQL chunk text and a map of source table names to staging table names.
- Replace backticked identifiers such as `` `wp_posts` `` with `` `ssc_tmp_abcd_wp_posts` ``.
- Rewrite `DROP TABLE IF EXISTS`, `CREATE TABLE`, and `INSERT INTO` statements generated by current backup exporter.
- Leave string literals untouched by only replacing backticked identifier tokens.

This is intentionally narrow and matches the plugin-generated dump format.

### `DatabaseChunkImporter`

New installer class:

`super-sheep-copy/installer/restore-engine/DatabaseChunkImporter.php`

Responsibilities:

- Connect with `mysqli` using parsed credentials.
- Disable multi-statement assumptions by executing individual SQL statements split from plugin-generated dump chunks.
- Execute rewritten statements in order.
- Return table count, chunk count, statement count, and warnings.

Statement splitting can be simple for this slice because current plugin-generated SQL chunks use semicolon-terminated statements and do not emit stored procedures/triggers.

### `DatabaseImportPreparationManager`

New installer class:

`super-sheep-copy/installer/restore-engine/DatabaseImportPreparationManager.php`

Responsibilities:

- Enforce gates:
  - `restore_confirmed` is true
  - `rollback_prepared` is true
  - `rollback_database_dump` is non-empty
  - `database_import_staged` is not already true
  - config is not locked
- Read database credentials with `WpConfigReader`.
- Validate connection with `DatabaseConnectionTester`.
- Read manifest and chunks from staged archive.
- Build staging table names using restore job id and source table name.
- Use `SqlTableNameRewriter` and `DatabaseChunkImporter`.
- Update installer config:
  - `database_import_staged`
  - `database_import_staged_at`
  - `database_import_table_count`
  - `database_import_chunk_count`
  - `database_import_statement_count`
  - `database_import_staging_tables`

Staging table names should be deterministic for one run:

`ssc_tmp_<8-char job hash>_<sanitized source table name>`

Sanitization keeps letters, numbers, and underscores, replacing other characters with `_`.

## Bootstrap UI

Add a new installer section after rollback preparation:

- If restore not confirmed: show database import requires confirmation.
- If rollback not prepared: show database import requires rollback preparation.
- If rollback DB dump missing: show database import requires database rollback dump.
- If staged import complete: show imported table/chunk counts and state that table replacement is not implemented yet.
- If ready: show POST form with `name="stage_database_import"` and button `Import Database to Staging`.

POST handling:

- Action key: `stage_database_import=1`.
- Reuse token hidden field.
- On success, reload config and show `Database import staged`.
- On failure, show safe warning message.

## Safety

- Do not execute `DROP TABLE` against original destination table names.
- Rewritten `DROP TABLE IF EXISTS` may execute only against staging table names.
- Do not execute `RENAME TABLE`, `TRUNCATE`, `DELETE FROM`, or `UPDATE`.
- Do not render DB password.
- Do not store DB password in manifest or new config fields.
- Do not extract ZIP entries to arbitrary paths.
- Keep installer token gate unchanged.
- Keep staged import idempotent by refusing to run again when `database_import_staged` is already true.

## Testing

Unit tests cover:

- Manifest reader accepts valid `database/tables.json` with chunk entries.
- Manifest reader rejects unsafe chunk names and missing chunk entries.
- SQL rewriter rewrites backticked table identifiers and leaves quoted string values untouched.
- Chunk importer can be tested with fake executor boundaries for statement splitting and counts.
- Import manager rejects missing confirmation, missing rollback, missing DB rollback dump, locked config, and repeated import.
- Import manager records config metadata on successful fake import.
- Bootstrap renders import readiness/gating/status and does not expose secrets.

No real MySQL integration test is required in this slice.

## Success Criteria

- Installer has a token-gated database staging import action.
- Import can read the backup archive database manifest/chunks.
- SQL is rewritten to staging table names before execution.
- No destination table replacement exists.
- Full lint and PHPUnit pass.
- Git worktree is clean after commits.
